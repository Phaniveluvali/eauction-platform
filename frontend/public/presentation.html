Core Bidding Technology

Sub-Millisecond Atomic Bidding (Go + Redis Lua)

How Redis Lua scripting guarantees strict linearizability and eliminates race conditions.

The High-Concurrency Challenge

In traditional database-driven auctions, when two buyers submit $10,000 at the exact same millisecond:

  • ✗ Race Condition: Both read the same price and attempt an update, causing lock waits, timeouts, or split-brain highest bidders.
  • ✗ Database Bottleneck: Thousands of concurrent bids lock rows in SQL, grinding transactions to a halt.

The Redis Lua Solution

Redis executes Lua scripts as a single atomic unit of work on its single-threaded event loop:

  • ✔ Strict Linearizability: Bids are strictly ordered in microseconds; impossible for two bids to collide.
  • ✔ Instant Validation: Checks auction status, end-time, minimum increments, and bidder ID in memory (< 1ms).
  • ✔ Immediate Fan-Out: Validated bid is broadcast to all active buyers via WebSockets before touching the disk.
1. Buyer Submits Bid
→
2. Go Engine Dispatches Lua
→
3. Redis Mutates Hash (<1ms)
→
4. WebSocket Push to All Buyers
Stateful Reliability

Redis Sentinel 3-Node Failover Quorum

Automated heartbeat monitoring, leader election, and topology discovery ensuring zero downtime during node outages.

3-Node Sentinel Quorum

Three independent Sentinel monitors continuously ping Redis Master and Replica pods every 1,000 milliseconds.

3-Second Automatic Failover

If the master node crashes, Sentinel nodes establish a 2/3 quorum agreement, elect the standby replica, and promote it to master within 3 seconds.

Dynamic Client Discovery

The Go bidding engine listens to Sentinel Pub/Sub notifications, automatically re-pointing its connection pool to the new master without restarting.

Business Impact for Management

Even in the rare event of a physical server failure or hardware crash on the database host, active auctions remain intact, no bids are lost, and auction closing timers do not freeze.

Event Architecture

Decoupling high-speed in-memory bidding from durable relational database persistence.

Asynchronous Decoupling

Slow database queries or disk writes can never slow down the live auction. Redis handles immediate speed; Kafka handles guaranteed durability.

Zero Message Loss

Kafka retains an append-only commit log on persistent storage. If a database goes offline for maintenance, events wait safely in Kafka until it recovers.

Auditability & Analytics

Every bid event payload is replayable, enabling real-time analytics, settlement reconciliation, and AI anomaly detection downstream.

Data Tier Scalability

PostgreSQL Read/Write Splitting & Streaming Replication

Segregating heavy catalog read queries to standby replicas while protecting transactional writes.

Write Primary (eauction-postgres:5432)

Dedicated strictly to transactional state changes:

  • ✔ INSERT INTO bids (Recorded from Kafka)
  • ✔ User registration, KYC updates, and password changes
  • ✔ Auction lifecycle transitions (SCHEDULED → ACTIVE → CLOSED)
  • ✔ Financial ledger entries and payment settlement invoices

Read Standby (eauction-postgres-replica:5432)

Dedicated to high-volume read traffic (95% of queries):

  • ✔ 2,077 vehicle catalog browsing, filtering, and pagination
  • ✔ Vehicle inspection report downloads and spec queries
  • ✔ Historical bid logs and buyer past-bid review
  • ✔ Physical streaming replication lag is negligible (< 5 ms)

Automatic Spring Routing

Spring Boot's LazyConnectionDataSourceProxy inspects transactions: methods annotated with @Transactional(readOnly = true) route directly to the Standby Replica, eliminating read/write lock contention.

Zero Cascade Failures: Microservice Bulkheading

Traditional Monolith vs. AJ Auctions Bulkhead

In older monolithic architectures, if the bidding service or payment gateway crashes, the entire website displays a blank screen or 500 error.

In AJ Auctions, each microservice operates inside an isolated fault domain. A failure in one service is strictly contained.
